# j02: Walk-in new patient onto today's list

Persona: reception (Sunita Patil). Script: `scripts/ux/journeys/j02-walk-in-new-patient.cjs`. Story: FRONT-DESK-05.
Screenshots: `output/ux-journeys/scratch/j02/` (shared stack) and `output/ux-journeys/j02-check/j02/` (fresh seed).

Route scripted: sidebar Patients, "New Patient", fill the long "Create Patient" form, set Patient Type = Walk-in, pick a doctor, "Create". This is the only route that registers and books in one go, and the form itself advertises it (`PatientsManagement.tsx:902`). The other route (Appointments page, type name, "Add New Patient", click a Confirmed tile, "Confirm Booking", about 7 to 8 actions, FRONT-DESK-04) lets the receptionist choose the time and ends on the calendar.

## Headline finding (measured)

The receptionist cannot get this patient onto TODAY's list on the seeded clinic. The screen reports success anyway.

- Run on the shared stack, 15:02 IST: toast "Walk-in appointment booked. Booked into the Confirmed calendar for 14 Nov 2026 at 11:30-12:00" (`06-booked-toast-on-patients-list.png`). Today (13 Nov) still had 15:30, 16:30, 17:00, 17:30 free for Dr. Menon.
- Cause (measured from API and backend log): every `POST /appointments` for Dr. Menon today returns 500 (`databaseCode P2002`, `backend.log`). The seeded 15:15 appointment has `tokenNumber = null`; `nextDoctorToken` (`backend/src/modules/appointments/appointments.service.ts:1337-1348`) sorts by `tokenNumber desc`, Postgres puts NULL first, so the next token is computed as 1 and collides with the existing token 1 on every retry (`withTokenRetry`, line 1350). Suspected: the same happens in production for any day that has one appointment with a null token.
- The walk-in loop swallows the error (`catch { // Ignore and try next day }`, `PatientsManagement.tsx:587-589`) and moves on to tomorrow. The toast does name the date but in the same size and colour as an ordinary success; a receptionist who reads "Walk-in appointment booked" and goes back to the patient will have told him he is in today's queue when he is not.
- Because of this the script's goal is verified as "patient exists and has one appointment with Dr. Menon", and the goal sentence records the date and whether it is on today's list. On the seed it reads "NOT on today's list". The ideal journey below assumes the booking works.

## 2. Take-away Pass

**Dashboard** (`01-dashboard.png`). Not needed for this journey except as the launch pad. It offers no registration or walk-in button although the receptionist's most frequent errand is exactly this. "Total Users / Active Users / Total Branches / System Status" are admin metrics a front desk never acts on (not part of this journey; noted only).

**Patients list** (`02-patients-list.png`). One primary action ("New Patient", dark button), good. Removable for this task: title "Patients Management" and the sub-title "Manage patient records and information" and, directly under it, a second heading "Patients" with "Search, add, and manage patient records" (the page states its purpose twice, `page.tsx:13` and `PatientsManagement.tsx:755-756`), "Clear Filters", "Export CSV", the gender/consultation/date-range/page-size filters and the "Quick Guide" button, none of which the walk-in uses. The card below states a third time "Patient Records / Manage and view all patient information". The list was still empty ("No patients found") in the screenshot taken straight after load, a loading state shown as an empty state.

**Create Patient dialog** (`03`, `04`, `05`). 14 visible fields for a task that needs 2 to 4. Nothing is marked required (no asterisk anywhere), yet blank First Name or Phone is rejected, and the other required-looking field, Gender, pre-selects a wrong value. Removable or deferrable: ABHA ID with its hint, Email, Address, Emergency Contact, "How did the patient hear about us?", Consultation Type, Primary Doctor with its hint (all optional, none needed to be seen by a doctor). Patient Type at the bottom is the one switch that changes what the Create button does, yet it is the last thing on the form and the button label stays "Create". Exactly one primary action exists ("Create"), but it is below the fold at the 850px test viewport; the dialog scrolls internally (`ui/dialog.tsx:63`), so the receptionist has to scroll to find both the Walk-in fields and the button. The fields in the walk-in block (Appointment Type, Room) default sensibly and can simply be hidden.

**Result** (`06`). After success the dialog closes, the list refreshes and a transient toast carries the only record of what was booked (date and time). Information that matters most (when is he seen, token number) is the smallest and shortest-lived element on the screen.

## 3. The Simpler Version

1. On the dashboard (or anywhere) click "Walk-in patient". A small dialog opens with doctor preselected (last used or the only doctor on duty) and "Male / Female / Other" as visible choices with none preselected.
2. Type the name, age and phone; pick gender (one click).
3. Click "Register and add to today's list".
4. The screen shows "Farhan Qureshi is #4 for Dr. Menon at 15:30 today" with buttons "Open list" and "Register another". If today has no free slot, it says so and offers tomorrow as an explicit choice instead of silently moving him.

Everything else (ABHA, email, address, emergency contact, referral source) lives on the patient's profile and is asked later, once, by whoever needs it.

## 4. Clarity Issues

- Two vocabularies for one action: sidebar says "Patients", button says "New Patient", dialog says "Create Patient", submit says "Create". The Appointments page calls the same record "Add New Patient" and marks required fields with `*`; this dialog marks none (story FRONT-DESK-05, measured in `05-form-filled.png`).
- "Patient Type: Walk-in / Non walk-in" describes how the patient arrived, but is used as a switch for "book him now". A receptionist registering a phone caller does not think "non walk-in". "Doctor (for walk-in)" and "Appointment Type (walk-in)" repeat the jargon.
- "Primary Doctor: Automatic" and "Doctor (for walk-in)" are two doctor fields with different meanings in one dialog.
- Walk-in doctor field is silent when empty: choosing Walk-in with no doctor saves the patient and books nothing, with no warning (`:500` condition).
- "Create" does not say it will also book. Success message "Walk-in appointment booked" does not say today or tomorrow in a form that stands out.
- Gender "Other" pre-selected is a data-quality problem and reads as an answer the receptionist gave.
- Age field label "Age (years)" with placeholder "e.g. 35" restates itself (see Subtext).

## 7. Verdict

**Acceptable on step count, convoluted on outcome.** 13 actions against an ideal of 7 is 6 extra, which on count alone would be convoluted, and the extra steps are mostly forced decisions with wrong or missing defaults (Gender, Patient Type, Doctor) and a 14-field form with nothing marked required. The route is concealed too: the sidebar has no "walk-in" word, and the receptionist must learn that a dropdown at the bottom of the form turns registration into booking. More serious, the journey's promised result (patient on today's list) fails on the seeded clinic with a success toast, because of the null-token bug and the swallowed error. Measured: 13 actions, 3 decisions without a default, 0 typed twice, 6 screens.
