# Prescription PDF acceptance pipeline

Run from the repository root:

```sh
npm run test:prescription-pipeline
```

Requires the repository's npm dependencies and Poppler (`pdftotext` on PATH,
or `PDFTOTEXT_BIN=/absolute/path/to/pdftotext`).

The pipeline starts an ephemeral Nest HTTP server on localhost and uses the
frontend ApiClient against it. It exercises DTO validation, the prescriptions
controller, prescription and visit services, the idempotency interceptor, and
real PDFKit rendering. Authentication uses a synthetic test doctor; persistence
uses an isolated in-memory transactional fixture. No production records or
notifications are created. This is an API integration acceptance test, not
verification of PostgreSQL, production authentication, or browser downloads.

Assertions cover creation, clinical and medication readback, replay of the same
creation key, sequential A -> B -> A edits, current PDF text, byte length and PDF
signature, download events, missing idempotency headers, and missing records.
Poppler parses the generated bytes and verifies patient, doctor and medicine text.

Generated samples (synthetic data only):

- `output/pdf/prescription-pipeline.pdf`
- `output/pdf/prescription-pipeline-updated.pdf`

Client orchestration is available as `apiClient.createPrescriptionAndPdf(payload,
{ idempotencyKey })`. A PDF failure does not undo the saved prescription; retry
creation with the same key, or regenerate the PDF for the saved prescription ID.
Each new update and PDF request gets a new key, retained within transport retries,
so previous edit states and old PDFs are not replayed for a new operation.

The existing Print Preview / Download PDF UI still uses its browser renderer.
This pipeline validates the server PDF path; it does not replace that layout.

## Browser download acceptance

```sh
npm run test:prescription-browser
```

Requires Google Chrome (override its executable with `CHROME_PATH`) and Poppler's
`pdfinfo` on PATH. The runner starts the frontend on port 3000 if needed, or uses
an already-running frontend. Set `RX_FRONTEND_URL` to use another local frontend.
It stops only the frontend process it started itself.

The browser drives the actual prescription UI and Paged.js renderer. API requests
are forwarded to the isolated Nest fixture described above. Download completion
is observed through Chromium download events; downloaded files must have a PDF
signature and exactly the same number of pages as the preview.

Coverage includes clinical fields and saved examination, medication add/remove
and presets, creation/readback, preview/download, edits and fresh downloads,
reload, medication and fields-only templates, template creation/application/
deletion, multi-page history, and failed-save download blocking and recovery.
The empty-phone WhatsApp guard is tested without sending any messages.

The browser renderer converts modern CSS colors in a private rendering clone
and exports each already-paginated page exactly once. These checks guard against
html2canvas's unsupported `oklch` error and extra blank trailing PDF pages.
Detailed examination remains saved without adding it to the printed layout.

Evidence is written to `output/prescription-browser/`: `network.json` contains
completed checks and request outcomes; PDF samples and screenshots support visual
review. The browser PDFs are rasterized, so PDF text extraction is not a content
assertion; preview text checks and rendered-page visual review complement the
byte/page checks. Use the test process exit status as the overall pass/fail signal.

Not covered: production authentication, PostgreSQL persistence, live medication
search/inventory integration, external translation, delivered WhatsApp/email,
or the operating-system print dialog and physical printers. This is repeatable
synthetic integration coverage, not certification of every production workflow.
