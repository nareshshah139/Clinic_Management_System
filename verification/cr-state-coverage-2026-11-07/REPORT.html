How this was verified

  • A planner takes each model and generates browser paths that together cover every transition. When an edge fails it plans new routes around it, so one failure cannot hide the edges after it.
  • An edge counts as passed only when the state it leads to passes its checks: visible text, aria state, element position in the viewport, and database rows where the CR is about storage or permissions.
  • Every model was broken on purpose at least once (a skipped click, a wrong expected value, a removed warning) to prove its checks go red.
  • Each feature also had a pass at phone width (390 × 844). Problems found there were fixed and are listed under each CR.
  • Unit and component tests were added alongside. On the final code 662 backend and 825 frontend tests pass across the affected suites, and neither app has type errors beyond the ones that existed before this work.

CR-21 · Visits → Visit Documentation

Patient identity stays on screen

The header line reads the patient from the visit, not from a one-row list, and shows name · age · sex · doctor · slot · visit type. It is sticky while the form scrolls, and collapsing Patient Context hides only ID, phone and recent visits.

Found during verification

  • fixedWith Patient Context open, the visit form overflowed sideways, so scrolling to Save Draft slid the identity line under the sidebar (name hidden at 1280px). The form layout now shrinks and stacks; 0 of 42 width × tab × context combinations overflow, down from 18.

CR-22 · Visits → On Examination

On Examination collapses

The block is collapsed by default, opens from its heading (click, Enter or Space), opens on its own when the visit already has examination data, never auto-closes, and remembers each doctor's last choice.

Found during verification

  • openThe CR asks to keep a separate free-text Examination field (from CR-05) expanded. No such field exists on the form, so the whole block collapses. Please confirm with the clinic.
  • openExamination findings do not appear in the printed prescription. This predates the work and was already listed under CR-08.

CR-28 · Inventory → Purchases → Terms of Trade

Terms of Trade

Doctors record discount, scheme, minimum expiry, margin, PTR and a note per distributor and product, in three steps (Distributor → Items → Scheme → Review). Staff read the same terms without edit controls; the API refuses their writes. Purchase invoice entry shows the agreed terms beside each matching line.

Found during verification

  • fixedOn a phone the Edit and Delete buttons sat off screen in the last table column, and a pending delete had no way to back out. Actions now sit under the product name, with a Keep button.
  • openPhase 2 (automatic invoice checking, Returnable flag), distributor-wide terms and change history were not built, as the CR defers them.

CR-30 · Inventory → Stock → Approve corrections → New items

Doctor approval for new items

Staff who add an item create a request instead; a badge tells doctors; approving creates the item in one transaction, rejecting needs a note. Double approval creates exactly one item, and the pharmacy assistant's create action goes through the same gate. Opening-stock imports by pharmacy staff work as before and are outside the approval flow.

Found during verification

  • fixedNothing warned about duplicates by name, against the CR's own purpose. Doctors and staff now see existing items with the same name, SKU or barcode, and other pending requests for the same name.
  • fixedAfter a second doctor had already reviewed a request, the dialog stayed open and the error was hidden from screen readers. It now closes, refreshes and announces the outcome.
  • fixedDoctors landed on the price/stock tab even with new items waiting. They now land on New items.
  • openAn earlier version also refused bulk imports from staff. That broke the pharmacist's opening-stock import, which the repository's recovery tests cover, so imports now behave as before. Bringing imports under approval means turning each new import row into a request, a separate change.
  • openFound along the way, not caused by this work: the permission check matches exact names, but the PHARMACIST role's defaults are wildcards such as inventory:item:*, so a pharmacist without a personal permission list cannot add or view stock items. Pharmacists set up with explicit permissions are unaffected. Left unchanged because it alters access across the whole app.

CR-33c · Inventory → Purchases → Day-wise summary

Day-wise Summary report

One row per day with the bill-number range and visible gaps ("3 - 5 · gap: 4 (draft)"), GST slab groups CESS · 0% · 5% · 12% · 18% · 28% · 40% · Total, each with Base · SGST · CGST · IGST, a totals row, frozen left columns, Sales or Purchase, and CSV download. Days with no bills show as ₹0 rows.

Found during verification

  • fixedPharmacists and accountants got 403 on every pharmacy report, including the existing GST report: the routes need a permission no role was granted. A migration grants it.
  • fixedReception saw report entries it could not open. The menu now follows the same role rules as the API.

CR-33d · Inventory → Purchases → Item-wise margin

Item-wise Margin report

Tiles for sale, purchase, net GST and profit (₹ and %), one row per product with the CR's columns, highest margin first, sortable headers, an (i) tooltip with the formula on every column, search, item links and CSV download.

Found during verification

  • fixedRanges over a year were accepted (the day-wise report refuses them). Both now share the 366-day limit.
  • fixedOn a phone the item name scrolled away with the figures. The name column is now frozen.
  • openLines sold without a recorded cost stay in Sales Amt but are left out of Purchase, Net GST and Profit, flagged with a chip and a banner. So Sales − Purchase − Net GST equals Profit only on fully costed rows. This is a deliberate choice; adding purchase prices removes it.
